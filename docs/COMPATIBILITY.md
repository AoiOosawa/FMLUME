# FMLUME 互換性の方針

利用者の手元には、DAW のプロジェクトとプリセットファイルが残ります。新しい版でも**同じように開けて、同じ音で鳴る**ことを約束します。この文書は、その約束を守るために変えてはいけないものと、変えるときの手順を決めます（D-062）。

## いつから守るか

**最初に外へ配った版（予定: 0.1.0）から**守ります。0.x の間も同じです（ベータを試した人の曲を壊さないため）。それより前のビルドで保存したものは対象外で、これまでどおり変更してよい（D-036）。どの変更も `docs/DECISIONS.md` に理由と影響を書きます。

## 1. 変えないもの

| 対象 | 値 | 変えると起きること |
|---|---|---|
| プラグインの識別子 | メーカー `Chbw`、プラグイン `Fmlu`、Bundle ID `info.cheebow.fmlume`、名前 `FMLUME`（D-048） | DAW がプラグインを見つけられず、プロジェクトが開けない |
| ホストパラメーターの ID | 22 個（`docs/IMPLEMENTATION_STATUS.md` §3） | オートメーションとコントローラーの割り当てが外れる |
| ホストパラメーターの範囲・刻み・選択肢の順番 | 例: `master.gainDb` −60〜+12 dB、`master.quality` Eco / Standard / High | DAW はオートメーションを 0〜1 の値で記録するため、記録済みの動きの意味が変わる |
| プリセット・状態の中の名前 | キー名、列挙の名前（`"saw"`、`"lfo1"`、`"reverb"` など）、パラメーター ID（`op1.level` など） | 古いファイルの設定が読めなくなる |
| ファクトリープリセットの ID | `patchId` | お気に入りが外れる |

ホストパラメーターは**追加はしてよい**（`juce::ParameterID` の版番号を上げる。AU で必要）。削除・改名・範囲の変更はしない。不要になったものは、効かないまま残す。

## 2. ファイル形式

対象は 2 つ: プリセット（`.fmlume`、`schemaVersion` 2）と、DAW のプロジェクトに入る状態（`fmlumeState` 1。プリセット全体＋ホストの値＋編集済みの印）。

**足すだけの変更**（`schemaVersion` を上げない）

- 新しいキーは**省略できる**ようにし、省略時は今までの動作になる値にする。古い版は知らないキーを無視して読む。
- 列挙に新しい値を足してよい（効果の種類、波形、モジュレーションのソース、カテゴリ、パラメーター ID、テンポの分割など）。古い版は知らない値をその部分だけ既定値にして読み、ステータス行で知らせる。プリセット全体を拒否はしない（0.1.0 から。下の「古い版の読み方」）。

**意味が変わる変更**（`schemaVersion` を上げる）

- 既存のキーの意味・単位・範囲を変える、構造を変えるときは、`schemaVersion` を上げ、古い番号から変換する関数（`migrateNtoN+1`）を書く。古い形式のフィクスチャとテストを残す。
- 古い版は、自分より新しい `schemaVersion` のファイルを拒否する（中身を誤解して鳴らすより安全）。そのためこの変更は最小限にする。

**古い版の読み方（0.1.0 で入れたもの）**

- 知らないキー: 無視する。
- 知らない列挙の値: 既定値のまま読み、「このバージョンの知らない設定があり、既定値にした」と警告する。知らないパラメーターへのマクロの割り当ては外し、知らないソースの Mod Matrix の枠は空にする。知らない効果は並び順と一覧から外す。
- `pluginVersion` が自分より新しく、知らない値がないとき: 「新しい FMLUME で保存された。後から足された設定は無視した」と知らせる。
- 構造の誤り（型の違い、範囲外の数値、結線のループ、必須キーの欠落）は、これまでどおり拒否する。

## 3. 音

同じプロジェクトは、新しい版でも同じ音で鳴らなければならない。

- **見張り**: `tests/Integration/SoundRegressionTests.cpp` が代表 14 音色（各カテゴリの最初の音色と、LFO・トレモロ・トランスゲートを使う音色）を描き出し、20 ms ごとの左右と低域・高域の音量を `tests/Golden/sound_fingerprints.json` と比べる。許容差は 1 dB（CPU やコンパイラーによる丸めの違いは通し、エンベロープ・音量・フィルター・音色の変化は捕まえる。オペレーター 1 つを 5 セントずらしただけでも失敗することを確かめた）。arm64 と x86_64 の両方で通る。
- **音が変わる変更をするとき**は、次のどれかを選び、DECISIONS に書く:
  1. **不具合の修正として変える**: 明らかな誤り（クリック、ノイズ、計算違い）で、直した方が誰にとっても良いとき。音の差が小さいことを確かめ、指紋を記録し直す。
  2. **古い動作を残す**: 音作りに効いている動作を変えるとき。パッチに「エンジンの版」を持たせ、古いプロジェクトは古い動作で鳴らす（必要になった時点で `engineVersion` を省略可能なキーとして足す。省略時は 1）。
  3. **新しい設定として足す**: 新しい動作を選べるようにし、既定値は今までの動作にする。
- 指紋の記録し直し: `FMLUME_UPDATE_SOUND_FINGERPRINTS=1 build-core/tests/FMLUMETests integration`。理由のない記録し直しはしない。

## 4. ファクトリープリセット

- プロジェクトには音色の設定がまるごと保存されるので、ファクトリープリセットを直しても既存の曲は変わらない。名前・説明・音の手直しはしてよい。
- `patchId` は変えず、使い回さない（お気に入りが ID で覚えているため）。削除した ID も再利用しない。

## 5. 公開の前に確かめること

`docs/RELEASE_CHECKLIST.md` の項目に加えて:

- 識別子とホストパラメーターが上の表のとおりか（`auval -v aumu Fmlu Chbw` の出力、`PluginProcessor.cpp` の `ParameterID`）。
- `ctest` が通る（新しい版のファイルの読み込み、指紋、古い形式からの変換を含む）。
- 前の版で保存したプロジェクトとプリセットを、新しい版で開いて同じ音がするか（2 版目以降。前の版のファイルを `tests/Fixtures/valid` に足していく）。
